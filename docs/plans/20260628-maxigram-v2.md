# maxigram v2 — модульный монолит (Kotlin + Spring Boot 4.1 + Spring Modulith + jOOQ)

## Overview

Переработка проекта maxigram (соцсеть, изначально — бакалаврская ВКР 2024 г.) из набора
из 4 микросервисов (`user`/`chat`/`feed` + `api-service`-шлюз на gRPC, RabbitMQ, Keycloak,
Jmix/Vaadin-фронт) в **модульный монолит** на Kotlin/Spring Boot с переписанным фронтендом.

Защита ВКР не планируется — единственный критерий качества здесь инженерный:
читаемость, предсказуемость, отсутствие классов багов v1, поддерживаемость.

**Что меняется по сравнению с v1:**
- 4 микросервиса + gRPC + RabbitMQ → один монолит с модулями (Spring Modulith) и доменными событиями;
- Java → **Kotlin** (null-safety, `data class` для событий/DTO, лаконичность);
- JPA/Hibernate → **jOOQ** + Flyway (типобезопасный SQL, без cascade/lazy/N+1-магии);
- внешний Keycloak → встроенный **Spring Authorization Server** (свой модуль `identity`, всё в монолите);
- `api-service` без авторизации (identity из query-параметра) → **OAuth2 Resource Server**, identity из JWT (`sub`);
- Jmix/Vaadin без real-time → **React SPA** + REST + **WebSocket/STOMP**;
- добавляется модуль **уведомлений** (in-app + email);
- пакеты-копипаста `ru.maxizenit.backend.chatservice` → единый `org.maxizenit.maxigram` (reverse-DNS домена maxizenit.org).

**Что переносим из v1 (идеи, доведённые до рабочего состояния):**
профили/интересы/подписки; лента (посты, лайки, комментарии); обычные и анонимные чаты
со взаимной деанонимизацией; подбор собеседника по «похожести»; самоограничения (цифровое благополучие).

- `backend/chat-service` — чаты, анонимность, деанонимизация (логика сломана);

## Solution Overview

### Архитектурный стиль
Модульный монолит. Один деплой-артефакт, внутри — изолированные модули с явными границами,
проверяемыми **Spring Modulith** (`ApplicationModules.verify()` в тесте). Межмодульная связь —
только через публичные API модулей (named interfaces) и **доменные события**; прямой доступ к
внутренним пакетам и таблицам чужого модуля запрещён. Это сохраняет возможность вынести любой
модуль в отдельный сервис позже, без оверхеда сети/брокера сейчас.

### Модули
- `common` — общий kernel: типы-значения (`UserId`), утилиты, базовая конфигурация, обработка ошибок.
- `identity` — **Spring Authorization Server**: собственное хранилище пользователей, регистрация,
  пароли (Argon2), выдача OIDC-токенов, верификация email и сброс пароля. Также `CurrentUser` (resource side).
- `profile` — `UserProfile`, `Interest`, `Subscription`.
- `feed` — `Post`, `Comment`, `Like`, лента, счётчики.
- `chat` — `Chat`, `Message`, обычные/анонимные чаты, деанонимизация, WebSocket.
- `notification` — in-app уведомления (push через STOMP) + email; слушает доменные события других модулей.
- `matching` — подбор собеседника по похожести; слушает события, публикует результат.
- `wellbeing` — `SelfRestraint` (самоограничения).

### Доступ к данным
**jOOQ** как единственный слой доступа. Схема описывается миграциями **Flyway**
(`src/main/resources/db/migration`) — это источник правды. Классы jOOQ генерируются кодогеном
из применённой к временной БД схемы (Testcontainers/локальная БД на этапе сборки). Никаких сущностей
Hibernate, `cascade`, `mappedBy`, lazy-проксей и dirty-checking — только явные запросы. Каждый
модуль владеет своими таблицами; обращение к таблицам другого модуля — через его API.

### Безопасность и identity
`identity`-модуль поднимает **Spring Authorization Server** (OAuth2/OIDC): свой реестр клиентов,
выдача токенов, собственная модель пользователя (`app_user`), регистрация и флоу email-верификации/сброса
пароля. Остальное приложение — **OAuth2 Resource Server**: identity берётся исключительно из токена
(`JwtAuthenticationToken` → `sub` = `app_user.id`), а не из тела/параметров запроса. Все доменные
операции авторизуются по текущему пользователю.

### Уведомления
Модуль `notification` подписывается на доменные события Modulith (новое сообщение, подбор в анонимный
чат, новый подписчик, лайк/комментарий, а также события auth-флоу) и доставляет их двумя каналами:
**in-app** (push подписчику через STOMP) и **email** (Spring Mail). Email-инфраструктура переиспользуется
модулем `identity` для верификации/сброса пароля.

### Real-time
WebSocket поверх STOMP: подписка на чат (`/topic/chats/{chatId}`) и на личные уведомления
(`/user/queue/notifications`). Аутентификация WebSocket — тем же JWT при handshake.

### Фронтенд
React SPA (Vite + TypeScript), общение по REST, real-time — по WebSocket/STOMP. Аутентификация
через OIDC (Authorization Code + PKCE) к встроенному Authorization Server.

### Базовый пакет
Единый `org.maxizenit.maxigram` (reverse-DNS реального домена maxizenit.org). Конец разнобою
`ru.maxizenit` / `ru.maxigram` и копипасте `…backend.chatservice`.

## Technical Details

### Модель данных (Flyway-миграции, jOOQ-кодоген поверх)
Ориентировочные таблицы (точные типы/индексы фиксируются в задачах соответствующих модулей):
- `identity`: `app_user(id pk uuid, email unique, password_hash, email_verified, created_at)`;
  `email_verification_token`, `password_reset_token`; стандартные таблицы Spring Authorization Server
  (`oauth2_registered_client`, `oauth2_authorization`, `oauth2_authorization_consent`).
- `profile`: `user_profile(id pk → app_user.id)`, `first_name`, `last_name`, `birthdate`;
  `interest(id pk, name)`; `user_interest(user_id, interest_id)`;
  `subscription(subscriber_id, author_id)` — pk из двух колонок.
- `feed`: `post(id pk, author_id, text, created_at)`; `comment(id pk, post_id, author_id, text, created_at)`;
  `post_like(post_id, author_id)` и `comment_like(comment_id, author_id)` — раздельные таблицы лайков
  (в v1 одна таблица `like_` с двумя nullable-FK — заменяем на две явные).
- `chat`: `chat(id pk, first_participant_id, second_participant_id, anonymous, first_agreed, second_agreed,
  closed, new_chat_id)`; `message(id pk, chat_id, sender_id, text, created_at, read)`.
- `notification`: `notification(id pk, recipient_id, type, payload, read, created_at)`.
- `matching`: `match_request(user_id pk, created_at)`; `similarity_calc(id pk, first_user_id,
  second_user_id, age_sim, interests_sim, feed_sim, status)` — состояние расчёта в БД, не in-memory.
- `wellbeing`: `self_restraint(user_id pk, start_time, end_time)` — **с полями времени** (в v1 их не было).

### Ключевые потоки

**Идентификация.** `identity` выдаёт OIDC-токены, где `sub = app_user.id`. Каждый защищённый запрос
несёт JWT; `CurrentUser.id()` берётся из `sub`. Контроллеры не принимают `requesterId`/`authorId` от
клиента — только из контекста.

**Деанонимизация (исправление дефекта #3).** При согласии участника выставляется флаг **его** стороны
в `true` (в v1 для второго участника ставился `false`). Когда оба флага `true` — находится/создаётся
обычный чат, и в анонимный чат записывается `new_chat_id = <id нового чата>` (в v1 ошибочно брался
`getNewChatId()` нового чата, всегда `null`). Покрывается unit-тестами на обе стороны и идемпотентность.

**Подбор по похожести (исправление дефектов #5, #6).**
- Очередь кандидатов и состояние расчётов хранятся в БД (`match_request`, `similarity_calc`), а не в памяти
  инстанса — нет race condition и потери при рестарте.
- Вместо RabbitMQ — доменные события Spring Modulith: `matching` публикует запрос на сбор активности,
  `feed` отвечает событием, `matching` агрегирует и публикует результат; `chat` слушает результат и
  создаёт анонимный чат при превышении порога; `notification` уведомляет участников.
- Формула похожести интересов исправляется на симметричную:
  `(common/firstCount + common/secondCount) / 2` (в v1 второе слагаемое было `secondCount/common` → `Infinity`).
  Все коэффициенты защищаются от деления на ноль (проверка `count == 0`, а не только `isNaN`).
- Возраст — через `LocalDate`/`Period` с учётом месяца и дня (в v1 — deprecated `Date.getYear()`).

**Лента со счётчиками (исправление дефекта #9).** `likesCount`, `commentsCount`, `isLikedByCurrentUser`
считаются агрегатными запросами jOOQ (`COUNT`, `EXISTS`) одним-двумя запросами на страницу ленты, без
загрузки коллекций и N+1.

**Real-time сообщения (исправление дефектов #7, #10).** «Последнее сообщение» берётся запросом по
`created_at DESC LIMIT 1`. Новое сообщение рассылается подписчикам чата по WebSocket; фронт не опрашивает
по клику. Состояния кнопок (отправка/закрытие/деанонимизация) выводятся из состояния чата корректно.

## Development Approach
- **Подход к тестам: TDD** (тест → реализация → рефакторинг) для всей доменной логики.
- Завершать каждую задачу полностью до перехода к следующей; маленькие сфокусированные изменения.
- **Каждая задача обязана включать новые/обновлённые тесты** для своего кода (success + ошибочные/граничные сценарии).
- **Все тесты должны проходить перед началом следующей задачи** — без исключений.
- **Обновлять этот файл при изменении объёма работ.**

## Testing Strategy
- **Unit-тесты** — обязательны в каждой задаче (доменная логика: деанонимизация, формулы похожести, авторизация).
- **Интеграционные тесты** — на слой jOOQ и REST через **Testcontainers** (реальный PostgreSQL), на WebSocket-потоки.
- **Архитектурный тест** — `ApplicationModules.verify()` (Spring Modulith): границы модулей не нарушены.
- **e2e (фронт)** — Playwright по ключевым сценариям (логин, лента, отправка сообщения, согласие на деанонимизацию).

## Progress Tracking
- Отмечать выполненное `[x]` сразу по факту.
- Новые задачи помечать префиксом ➕, блокеры — ⚠️.
- Держать план в синхроне с реальной работой.

## What Goes Where
- **Implementation Steps** (`[ ]`): то, что делается в этом репозитории — код, миграции, тесты, документация.
- **Post-Completion** (без чекбоксов): внешние действия — деплой, ручная проверка, нагрузочное тестирование.
